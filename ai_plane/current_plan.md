# Текущий архитектурный план

## Кратко

EngineeringRAG развивается из вопросно-ответной RAG-системы в рабочее пространство с ИИ-ассистентом для проектной документации. Главная сущность будущего продукта — не чат сам по себе, а рабочее пространство проекта: папки, файлы, задачи, отчеты и чат как панель управления действиями над текущей папкой.

Первый вертикальный срез: интерфейс с областью видимости на уровне папки на Streamlit, загрузка одного целевого файла, запуск проверки документа по ссылкам на нормативно-техническую документацию (НТД), сохранение артефактов в форматах JSON/Markdown/PDF и возможность продолжить вопросы в том же чате.

## Зафиксированные решения

- LLM не создается отдельно на каждый чат. Все сессии чатов и задач используют общую точку доступа vLLM. На каждый чат создается состояние в приложении: сессия, выбранная папка, выбранный файл, задачи, артефакты и краткая рабочая память.
- Новое ядро делается отдельным сервисом `assistant_api`, а не расширением `retriever_api` или `user_api`.
- `assistant_api` — модульный монолит: рабочее пространство, папки, файлы, чат, задачи, артефакты, оркестрация, реестр задач, реестр инструментов, права доступа.
- Долгие задачи исполняются через Celery/Redis. Redis — брокер сообщений, PostgreSQL — источник истины по задачам/подзадачам/статусам/прогрессу, MinIO — исходные файлы и тяжелые артефакты.
- Очереди двухуровневые:
  - рабочие процессы продукта: `qa`, `document_audit`, в будущем `spellcheck`, `load_report`, `design_solution_check`;
  - очереди ресурсов: `quick_io`, `document_parse`, `retrieval`, `llm_short`, `llm_long`, `report_export`.
- Рабочий процесс жестко задан через реестр задач. LLM получает ограниченную свободу только в узлах принятия решений: классификация намерения, выбор подтипа проверки, формирование поискового запроса, оценка подтверждения утверждения найденными данными.
- LLM не формирует HTTP-запросы напрямую. Она возвращает типизированные вызовы инструментов, исполнитель проверяет JSON/Pydantic-схемы, права, лимиты и сам вызывает сервисы.
- MCP не является обязательной внутренней основой. Внутренние инструменты вызываются через типизированные клиенты Python/HTTP. MCP можно добавить позже как переходник для внешних систем.
- Пользовательские файлы никогда не смешиваются с индексом НТД. Они хранятся в отдельной зоне MinIO/PostgreSQL и являются объектом проверки, а не источником истины.
- Источник истины для НТД в первом рабочем процессе — текущий локальный корпус `QDRANT_COLLECTION`. Полного версионирования НТД пока нет, это технический долг.
- Рабочее пространство имеет дерево папок. Чат и задачи по умолчанию работают только с файлами напрямую в текущей папке, без рекурсивного обхода вложенных папок.
- На старте обрабатывается один активный целевой файл. Если выбрано несколько файлов, они идут пакетом из отдельных задач с ограничением параллелизма.
- Сопроводительные файлы пока не вводятся. Сценарий их использования не зафиксирован, поэтому не усложняем интерфейс и API.
- В папке может быть несколько чат-потоков. Пользователь пишет только в свои потоки. Чужие потоки доступны только для чтения по правам доступа.
- Права доступа закладываются сразу: наследуемые права от рабочего пространства/папки; файлы, потоки, задачи и артефакты наследуют права папки.
- Аутентификация остается в `user_api`. `assistant_api` проверяет bearer-токен через внутренний вызов к `user_api`.
- Streamlit остается первым интерфейсом для проверки пользовательского опыта. Бэкенд проектируется так, чтобы позже можно было заменить фронтенд.

## Первый рабочий процесс: проверка документа по НТД

Цель рабочего процесса — проверить ссылки и утверждения по НТД в одном пользовательском документе.

Основной маршрут:

1. Пользователь находится в папке рабочего пространства и выбирает один целевой файл.
2. Пользователь пишет естественный запрос: например, "проанализируй ПЗ на нормы".
3. Обработчик контекста связывает запрос с текущей папкой, целевым файлом и потоком.
4. Маршрутизатор определяет тип задачи `document_audit`.
5. Создается родительская задача `document_audit`.
6. Рабочий процесс извлекает текст через конвейер на основе MinerU.
7. Система извлекает ссылки на СП/ГОСТ/СНиП и локальный текст вокруг ссылки.
8. Для каждой ссылки запускается проверка через инструменты поиска и нормоконтроля.
9. Для каждой ссылки формируется строгий вердикт.
10. Создаются артефакты: JSON, Markdown, PDF.
11. Пользователь получает краткий ответ в чате и ссылки на артефакты.

Статусы проверки:

- `confirmed` — ссылка и утверждение подтверждены найденными данными.
- `document_not_found` — документ не найден в локальном корпусе НТД.
- `section_not_found` — документ найден, но пункт/таблица не найдены.
- `quote_mismatch` — пункт найден, но цитата или фрагмент текста не совпадает.
- `claim_unsupported` — пункт найден, но проектное утверждение не подтверждается.
- `insufficient_context` — данных недостаточно для уверенного вывода.

## Артефакты

Для каждой задачи проверки сохраняются:

- `audit_result.<guid>.json` — полный структурированный результат;
- `audit_report.<guid>.md` — человекочитаемый отчет и источник для интерфейса;
- `audit_report.<guid>.pdf` — экспорт из Markdown/HTML.

В PostgreSQL хранится краткая сводка: `job_id`, `status`, `owner`, `folder_id`, `file_id`, `summary`, `error`, ссылки на артефакты в MinIO.

## Память и продолжение диалога

Сырая история чата не является контекстом для LLM и не подается целиком в промпт.

Используется ограниченный обработчик контекста, который учитывает:

- текущую папку;
- активный целевой файл;
- последнюю задачу/отчет;
- выбранный артефакт;
- идентификаторы найденных подтверждений;
- краткую рабочую память.

Ответы LLM не становятся подтверждающими данными. Подтверждением служат только исходные пользовательские документы, НТД, будущая библиотека проектных решений и структурированные результаты проверок.

## Ограничения и технический долг

- Нет полноценного версионирования корпуса НТД. В отчетах фиксируем `checked_at`, `qdrant_collection`, `corpus_label=current`.
- Библиотека проектных решений института пока не формализована и не входит в первый рабочий процесс.
- Орфографическая и языковая проверка не входит в первый рабочий процесс, но добавляется позже как отдельная подзадача.
- Сопроводительные файлы откладываются до появления понятного сценария использования.
- MCP можно добавить позже, если появится реальная внешняя интеграция.
