# Хронология диалога и решений

## 1. Исходная идея

Пользователь описал цель: расширить текущую EngineeringRAG систему до AI-проверки
документов. На вход должен подаваться Word или PDF. Система должна:

- проверять ссылки на документы и говорить, нужно ли их обновить;
- проверять наличие и актуальность пунктов НТД;
- использовать текущую систему поиска как инструмент;
- в будущем проверять проектные решения по библиотеке проектного института;
- рассмотреть агентную архитектуру с декомпозицией задач.

Пользователь попросил использовать подход `grill-me` и разрешил спорить.

## 2. Факты по репозиторию

Было проверено текущее состояние проекта:

- есть `services/retriever` как FastAPI сервис поиска и генерации ответа;
- есть `SearchPipeline`, `QdrantRetriever`, `rewrite_query`, `compose_answer`;
- есть Qdrant, MinIO, PostgreSQL, vLLM, Airflow, MinerU, Docling;
- есть Streamlit UI;
- есть `user_api` с пользователями, сессиями, настройками и историей поиска;
- текущий `/search` решает один Q&A-запрос, но не делает аудит входного файла.

Вывод: текущий retriever должен стать tool/service для новых режимов, а не
разрастаться в полное AI-ядро.

## 3. Коррекция цели

Пользователь уточнил, что не хочет быстрый MVP ради скорости. Цель - сохранить
Q&A-систему и расширить ее до более общей системы с агентными режимами:

- проверка документов;
- помощь с шаблонами и отчетами по нагрузкам;
- вопросы по НТД;
- будущие сценарии декомпозиции задач.

Зафиксировано: скорость важна меньше качества и правильной архитектуры.

## 4. Архитектурный спор про “агентов”

Обсуждалась идея главной модели и субагентов.

Позиция assistant:

- не делать свободную агентность ради агентности;
- не запускать отдельную LLM на каждый чат;
- использовать общий vLLM inference endpoint;
- на каждый чат заводить session/task state в приложении;
- “субагенты” должны быть логическими worker-задачами/tools, а не отдельными
  моделями.

Пользователь согласился с уточнением: “голова на чат” означает session layer,
а не отдельный экземпляр модели.

Решение:

```text
Chat/Task Session
  -> Router / Planner
  -> Task Graph
  -> Queue
  -> Workers
  -> shared vLLM
  -> tools: retriever, parser, verifier, report composer
```

## 5. Жесткость workflow

Пользователь описал идею:

- заранее готовится список задач, которые умеет система;
- задачи добавляются постепенно;
- к каждой задаче есть набор сервисов;
- LLM не может получить данные из векторной базы без поискового сервиса;
- LLM должна иметь некоторую локальную гибкость, например решать, нужно ли
  переформулировать фрагмент перед поиском.

Решение:

- вводится task registry;
- у каждой задачи есть жесткий workflow;
- внутри workflow есть decision nodes;
- LLM принимает только локальные решения по заданной схеме.

## 6. Пользовательские документы и НТД

Пользователь подчеркнул: файлы пользователей точно не должны смешиваться с НТД.

Решение:

- пользовательские файлы хранятся отдельно в MinIO;
- metadata, ownership, chat/job summary хранятся в PostgreSQL;
- НТД остается отдельным источником истины;
- пользовательский документ является объектом проверки.

## 7. Workspace-first вместо chat-first

Пользователь предложил интерфейс не как главный чат, а как рабочее пространство:

- слева дерево проекта;
- рядом файлы в папке;
- справа AI-чат;
- пользователь сам создает папки и загружает файлы;
- LLM работает с файлами текущей папки.

Assistant поддержал это направление:

- это не чат-бот с файлами, а инженерное рабочее пространство с LLM-ядром;
- LLM не должна иметь прямой доступ ко всем файлам;
- доступ должен идти через folder scope, права и сервисы.

Решение: целевой продукт - workspace-first.

## 8. Folder-scoped context

Пользователь уточнил структуру:

- объект/проект содержит сложное дерево папок;
- чат привязан к конкретной папке;
- агент видит только документы в текущей папке;
- внутрь вложенных папок по умолчанию ходить нельзя.

Решение:

- чат и задачи работают только с direct files текущей папки;
- рекурсивный анализ папок не включается по умолчанию;
- если нужен рекурсивный анализ, это будет отдельный явный режим в будущем.

## 9. Составные запросы

Обсуждались запросы вида: “проанализируй ПЗ на нормы и проверь орфографию”.

Решение:

- один пользовательский запрос может создать parent job;
- parent job содержит несколько subtasks;
- subtasks выбираются только из разрешенного каталога задач.

## 10. Роли файлов

Пользователь предложил ограничение: одновременно обрабатывать только один файл
из-за ресурсов. Если у клиента больше ресурсов, лимит можно увеличить настройкой.

Также обсуждался вопрос `target file` и `context file`.

Решение:

- на ближайшем этапе есть один active target file;
- context files пока не вводятся;
- если выбрано несколько файлов, они идут как отдельные target jobs с лимитом
  параллелизма.

## 11. Очереди и выполнение jobs

Пользователь предложил Celery/Redis, так как хочет возможность масштабирования.

Assistant уточнил:

- Redis не должен быть источником истины;
- Redis/Celery нужны для доставки задач и исполнения;
- PostgreSQL хранит надежное состояние jobs/subtasks/progress;
- MinIO хранит файлы и artifacts.

Решение:

- Celery/Redis используются как execution layer;
- PostgreSQL - state store;
- MinIO - artifact store.

## 12. Двухуровневая очередь

Пользователь сначала думал об очередях по типам задач: Q&A, анализ документа,
другие режимы.

Assistant объяснил различие:

- product workflows - то, что видит пользователь;
- resource queues - то, что реально нагружает CPU/GPU/Qdrant.

Решение:

- сверху product workflow: `qa`, `document_audit`, будущие режимы;
- внутри resource queues: `quick_io`, `document_parse`, `retrieval`,
  `llm_short`, `llm_long`, `report_export`.

## 13. Q&A в новом интерфейсе

Пользователь описал сценарий: после анализа документа инженер задает уточняющие
вопросы по НТД в том же чате.

Решение:

- Q&A остается частью единого folder-scoped чата;
- router перенаправляет нормативные вопросы в текущий `retriever_api`;
- связь с предыдущим audit job сохраняется через artifacts/evidence, а не через
  сырой prompt history.

## 14. Память и история чата

Пользователь не хочет подавать в LLM всю историю чата, потому что это шум,
дорого и плохо для слабой модели. Но пользователи могут задавать вопросы про
предыдущие ответы и отчеты.

Assistant предложил разделить:

- chat history - хранится для UI и аудита;
- working memory - короткое состояние последней работы;
- evidence/artifacts - структурированные результаты, которые можно точечно
  подтянуть.

Решение:

- добавляется bounded context resolver;
- он связывает фразы пользователя с текущей папкой, файлом, job, artifact,
  evidence;
- вся история чата не подается в LLM.

## 15. MCP и tools

Пользователь понимал MCP как файл с инструкцией, логином, паролем и списком
команд.

Assistant уточнил:

- MCP - это протокол client/server для tools/resources/prompts;
- LLM не должна писать сырой HTTP;
- LLM должна возвращать structured tool calls;
- executor валидирует и вызывает сервис.

Решение:

- внутри системы делается tool registry;
- секреты хранятся в env/secrets, а не в prompt/skill-файлах;
- MCP можно добавить позже как adapter.

## 16. Первый вертикальный срез

Пользователь выбрал первый вертикальный срез:

- workspace;
- folder-scoped chat;
- document audit.

Решение: первый workflow - document audit одного target file.

## 17. Scope document audit

Пользователь выбрал первый scope document audit: проверка ссылок на НТД.

Решение:

- орфография не входит в первый workflow;
- библиотека проектных решений не входит в первый workflow;
- оба направления добавляются позже как отдельные subtasks.

## 18. Источник истины по НТД

Пользователь выбрал локальный корпус, потому что системы версионирования и
истории НТД сейчас нет.

Решение:

- проверка идет против текущего локального Qdrant корпуса;
- в отчете нельзя писать “актуально вообще”;
- нужно писать “подтверждено по локальной базе НТД/current”.

## 19. Вердикты document audit

Пользователь выбрал строгие статусы по каждой ссылке.

Решение:

- `confirmed`;
- `document_not_found`;
- `section_not_found`;
- `quote_mismatch`;
- `claim_unsupported`;
- `insufficient_context`.

## 20. Парсинг документов

Пользователь считает, что для качества лучше всегда использовать MinerU, так
как документы будут смешанными: текст, сканы, таблицы, картинки.

Assistant согласился, но указал на риск MinerU: ресурсы, падения, восстановление.

Решение:

- MinerU-first для target files;
- обязательно через worker isolation, timeout/retry, сохранение промежуточных
  artifacts и перезапуск worker.

## 21. Формат результата

Пользователь уточнил:

- JSON сохранять в MinIO с GUID;
- metadata хранить в PostgreSQL;
- Markdown показывать в UI и сохранять в той же папке;
- PDF делать как базовый экспорт;
- LaTeX пока не нужен, если Markdown/HTML проще.

Решение:

- `audit_result.<guid>.json`;
- `audit_report.<guid>.md`;
- `audit_report.<guid>.pdf`.

## 22. Детализация отчета

Пользователь выбрал показывать все проверки.

Решение:

- отчет содержит сводку;
- таблицу всех ссылок и verdicts;
- проблемы выделяются;
- evidence подробнее раскрывается для неподтвержденных/сомнительных мест.

## 23. Оценка качества

Пользователь согласился, что нужен gold dataset, но подготовит данные позже,
так как без специалистов сложно быстро разметить корпус.

Решение:

- в архитектуре заложить формат датасета и eval runner;
- сам датасет наполнять постепенно.

## 24. UI stack

Пользователь выбрал Streamlit first.

Решение:

- первый workspace UI делается на Streamlit;
- UX будет не финальным;
- backend API должен быть чистым, чтобы позже перейти на полноценный frontend.

## 25. Граница сервисов

Пользователь подтвердил, что новый слой должен быть отдельным сервисом, но не
полным монолитом.

Assistant предложил модульный монолит.

Решение:

- создать `assistant_api`;
- внутри четкие модули;
- отдельные AI-сервисы можно выносить позже.

## 26. Права доступа

Пользователь хочет видеть чужие чаты read-only по правам, но писать только в
свои. В будущем нужны уровни, например инженер не видит чат ГИПа.

Решение:

- inherited folder ACL;
- пользователь пишет только в свои threads;
- чужие threads доступны read-only по ACL;
- будущая ролевая модель добавляется поверх этой структуры.

## 27. Progress UI

Пользователь выбрал polling, но после завершения прогресс нужно убрать.

Решение:

- Streamlit UI периодически запрашивает job status;
- во время выполнения показывает stage/progress;
- после завершения прогресс скрывается или сворачивается;
- техническая история остается в PostgreSQL.
