# Изменения для поиска в глубину по внутренним ссылкам

## Цель

Сделать так, чтобы найденный текстовый фрагмент с внутренней ссылкой вроде
`таблице 4`, `п. 6.1.7` или `приложение А` автоматически подтягивал целевой
чанк того же документа. Основной сценарий: запрос на норму находит пункт
`6.1.7`, а ретривер дополнительно возвращает части `Таблицы 4`.

## Что изменено

1. В `airflow/dags/common/txt_feature/cleaner.py` разделены типы ссылок:
   - `man_refs` теперь хранит только внешние нормативные ссылки: СП, ГОСТ,
     СНиП, СанПиН.
   - `cross_refs` хранит внутренние ссылки документа в нормализованном виде:
     `table:4`, `section:6.1.7`, `appendix:A`.
   - `anchor_refs` хранит якоря чанка, по которым на него можно сослаться:
     например, табличный чанк `Таблица 4` получает `anchor_refs=["table:4"]`.

2. Добавлен финальный пересчет ссылок после обогащения метаданными раздела.
   Это важно, потому что `section_id` появляется только после `_enrich_metadata`.

3. Самоссылки отфильтровываются:
   - если табличный чанк содержит `Таблица 4` и одновременно является якорем
     `table:4`, то `cross_refs` для него не включает `table:4`;
   - таблица больше не ссылается сама на себя.

4. В `airflow/dags/batch_pipline.py` в Qdrant payload добавлены и индексируются:
   - `cross_refs`;
   - `anchor_refs`.

5. В `services/retriever/app/` добавлен поиск в глубину:
   - обычный dense/sparse/hybrid поиск выполняется первым;
   - для верхних результатов берутся `cross_refs`;
   - ретривер делает `scroll` в Qdrant по тому же `filename` и `anchor_refs`;
   - найденные связанные чанки вставляются сразу после исходного результата;
   - поле `expanded_from` показывает, по какой ссылке чанк был подтянут.

6. В UI и контексте LLM добавлены поля:
   - `anchor_refs`;
   - `expanded_from`.

## Как это работает на примере

Текстовый чанк:

```text
6.1.7 Расстояния ... принимаются не менее указанных в таблице 4.
```

получает:

```json
{
  "cross_refs": ["table:4"],
  "anchor_refs": ["section:6.1.7"]
}
```

Табличные чанки `Таблица 4` получают:

```json
{
  "cross_refs": [],
  "anchor_refs": ["table:4"]
}
```

После обычного поиска ретривер видит `cross_refs=["table:4"]` и дополнительно
возвращает чанки, у которых `anchor_refs` содержит `table:4`.

## Параметры API

В `/search` добавлены параметры:

```json
{
  "expand_refs": true,
  "ref_depth": 1
}
```

`expand_refs=true` включен по умолчанию. `ref_depth` ограничен защитным лимитом
в коде ретривера, чтобы не раздувать контекст рекурсивными ссылками.

## Что нужно сделать после деплоя

Нужно переиндексировать документы в Qdrant через Airflow pipeline. Старые точки
не содержат `anchor_refs`, поэтому поиск в глубину начнет работать только после
повторного прогона chunking/indexing.

## Ограничения и риски

- Качество OCR таблиц не исправлялось: это отдельный уровень проблемы.
- Внутренние ссылки нормализуются регулярными выражениями, поэтому экзотические
  формулировки могут потребовать расширения паттернов.
- Сейчас связь ищется внутри того же `filename`. Междокументные ссылки через
  `man_refs` сохранены, но автоматическое раскрытие внешних СП/ГОСТ пока не
  включено.
- При очень длинных таблицах подтягивается ограниченное число связанных окон,
  чтобы не перегружать ответ и Qdrant.
